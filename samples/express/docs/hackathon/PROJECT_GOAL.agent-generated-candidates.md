# 專案目標：診所情境生成式 AI 困難病人模擬

## 1. 一句話形容專案

診所輸入科別、資源與時間限制後，由 Agent 自動生成符合該診所情境的虛構病人與病例背景，讓醫師透過 Perxona Avatar 練習困難醫療溝通並取得回饋。

## 2. 目標使用者

台灣基層診所的第一線醫師，以及負責院內溝通訓練的診所管理者。

## 3. 想解決的問題

現有 Virtual Patient 多使用固定案例，或要求使用者自行設定病人背景、人格、情緒與病史；建立成本高，也難反映每間診所真實的設備、流程與時間限制。

困難醫療情境也不是單純的「壞病人」，而是病人期待、醫師回應與照護環境共同形成。例如病人要求 CT 時，診所有沒有設備、如何轉診、先前如何說明，都會改變互動。

因此本專案改成：

> **使用者只描述診所，Agent 負責生成可能的病人、病例背景與訓練重點。**

系統使用可觀察的行為傾向，不把角色標示為人格疾病；同時以 Avatar 呈現語氣、表情與姿態，使訓練不只是文字問答。

## 4. 最小資料設定與生成流程

### 原則

- 人工只輸入診所資料。
- 病人、病例背景、初始狀態與評分重點均由 Agent 生成。
- 案例皆為虛構訓練素材，不輸入真實病歷或個資。
- 醫師預覽並確認生成內容後才開始模擬。

### (1) Agent 生成可能的病人

系統依診所資料一次生成 **3 個候選病人**。每個候選只需顯示：

| 欄位 | 內容 |
| --- | --- |
| 病人摘要 | 年齡區間、生活背景與主訴 |
| 明確要求 | 想取得的藥物、檢查、保證或安排 |
| 互動傾向 | 一項主要可觀察行為 |
| 隱藏需求 | 真正擔心或想被滿足的需求 |
| 診所衝突 | 要求如何碰到診所限制 |
| 訓練焦點 | 本案例主要練習能力 |

內建互動傾向限縮為六類：

1. 反覆尋求保證／依賴
2. 細節與控制需求高
3. 不信任／防禦
4. 情緒表達強烈
5. 堅持特定藥物或檢查
6. 拒絕建議卻反覆就醫

使用者選定候選後，Agent 再補上說話方式、觸發點、安撫方式、隱藏資訊與初始狀態。

### (2) 使用者輸入的診所資料

#### 必填 4 項

| 欄位 | 範例 |
| --- | --- |
| 科別與主要服務 | 家醫科；一般內科門診 |
| 可提供的資源 | 抽血、心電圖、X 光 |
| 無法提供／需轉診的資源 | CT、MRI |
| 平均看診時間 | 每位病人約 7 分鐘 |

#### 選填 2 項

| 欄位 | 範例 |
| --- | --- |
| 轉診或追蹤方式 | 合作醫院轉診、兩週後回診 |
| 常見摩擦或當下壓力 | 常被要求不必要影像；候診人很多 |

若選填欄位留白，Agent 可以提出假設，但必須在預覽頁標示並允許重新生成。

### (3) Agent 生成病例與醫病關係背景

選定病人後，Agent 只生成本次模擬需要的最小背景：

| 欄位 | 內容 |
| --- | --- |
| 本次情境 | 主訴、明確要求與診所限制 |
| 既往就診 | 0–2 次關鍵互動：要求、醫師回應、病人感受 |
| 期待落差 | 病人想要什麼，目前合理能提供什麼 |
| 隱藏背景 | 焦慮來源或先前經驗，依對話逐步揭露 |
| 初始關係 | 信任、焦慮、合作意願（低／中／高） |
| 成功條件 | 2–4 個本次溝通目標 |

例如：病人前次因胸悶就診但未獲充分說明，本次帶著網路文章要求 CT；診所無 CT，病人表面要求檢查，實際想確認醫師沒有忽略重大疾病。

Agent 生成的醫療內容必須由醫師預覽確認；本產品不提供診斷或治療決策。

### (4) 對話狀態與簡化評分

對話中只追蹤三項狀態：信任、焦慮、合作意願（低／中／高）。

對話後只評四項，每項 0–2 分：

| 評分項目 | 判斷重點 |
| --- | --- |
| 理解需求 | 是否找到明確要求背後的擔心 |
| 同理與說明 | 是否回應情緒並清楚說明 |
| 界限與資源 | 是否守住專業界限並提供替代方案 |
| 合作與下一步 | 是否形成可執行的追蹤或轉診計畫 |

回饋固定包含：做得最好的一點、狀態變化、一個主要風險，以及一句可直接替換的建議說法。

## 5. 產品流程

```text
輸入診所資料
→ 生成 3 個候選病人
→ 選擇或重新生成
→ 生成病例與 0–2 次既往就診
→ 醫師預覽確認
→ Perxona Avatar 扮演病人
→ 對話後輸出評分與建議
```

## 6. Why Perxona

- Avatar 用語氣、表情與姿態呈現焦慮、不信任或挫折。
- 病人的表現會隨信任、焦慮與合作意願改變。
- 醫師必須觀察反應並即時調整說法，接近真實診間壓力。

若移除 Avatar，產品只剩文字案例生成器，會失去最重要的非語言觀察與臨場溝通訓練。這對應黑客松評分中占 60% 的 `Why Perxona`。

## 7. 黑客松 MVP

### 必須完成

- 診所資料輸入表單
- 生成並選擇 3 個候選病人
- 生成本次病例與最多 2 次既往就診
- Perxona Avatar 完成對話與基本情緒／動作表現
- 輸出四項評分與建議說法
- 一套固定 Demo 診所資料與腳本

### 本階段不做

- 真實病歷、個資或 HIS／EMR 串接
- 診斷或治療建議
- 完整長期病歷與永久多次就診狀態
- 多使用者權限、複雜人格量表或自訂評分權重
- 一開始支援所有科別與所有病人類型

## 8. 驗收與設計依據

同一份診所資料應能生成不同但合理的候選病人；選定後，病例必須與診所限制直接相關，Avatar 反應應符合三項狀態，最後提供四項分數與至少一句可採用的改寫。

- `困難型病人.pdf`：困難情境由病人、醫師與照護系統共同形成；處理原則包含傾聽、同理、合作、清楚界限與依互動特質調整溝通。
- `0829 Perxona Taipei Hackathon.pdf`：產品價值 30%、Why Perxona 60%、Demo 與說故事 10%。
